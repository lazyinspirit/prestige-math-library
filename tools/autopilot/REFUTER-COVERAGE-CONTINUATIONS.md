# One native Step-5 coverage correction

The ordinary `mathlib.step5.mts` stage table supports one opt-in, owner-reviewed fresh
native refuter dispatch through `refuter-continuations.mts` for an exact successful report whose coverage array
contains extra prerequisite context. This does not accept mathematics or waive
collection. Ordinary Step-5 collect and final checks still require exact scope.

The run-local `research/RUN-step5-refuter-continuations.json` is version 1,
identifies the run, `authorized_by: owner`, nonempty authorization, and exactly
one continuation. The entry identifies the existing unit, concrete reason,
completed writer-drain time, exact successful `previous_result` path/hash,
canonical `report_path`, old `report_sha256`, immutable `original_report`
archive path/hash, `scope_sha256`, the exact required `subjects` with id/path/raw
hash, and a correction `task` path/hash. Paths for archived/report/task evidence
must remain under the run's research prefix. The unique permitted label is
`refute-UNIT-coverage-correction-1`.

Only `5a-refute` changes. The ordinary table decorates that stage once; the
ready-pairs wrapper inherits the same route without a second decorator. The
active ordinary controller therefore sees the opt-in route directly. Its matcher excludes the exact old stable result and
admits the exact new stable native result filename; other units and stages keep
ordinary routing. The planner retains the ordinary refuter role, configured
model, read-only brief, schema, canonical result artifact and timeout, changing
only label and task. Before launch it verifies report, scope, subject bytes,
authentic original report against the successful receipt's output tail, task
and immutable archive. No required original read may be missing. After fresh
output replaces the canonical report, old observation guards use the archive;
they do not compare the new report to old report bytes.

The original session may be unavailable. The new worker must perform its own
complete read, with prerequisite context, rather than inherit an acceptance or
invent prior observations. It reports actual findings and separates extra
context reads into the coverage note. Preserve ordinary attempt/result archives
and archive the original report before enabling authorization. A completed
fresh attempt, including failure, prevents another planner launch; owner review
is required for a concrete new blocker. There is no repeated unchanged repair
loop, executor surgery, state reset, workflow revision change or synthetic
receipt. The owner reviews the proposal, commits code/docs and writes the
actual authorization; merely creating a proposal does not enable this route.
