## Why ordinary aliases and existing recoveries do not suffice

- `tools/step5-rounds.mjs`, `scopedInventoryContext`: frozen IDs, current manifest IDs and original `before` identities are strict canonical requirements. Its resolver returns a frozen/baseline identity before consulting aliases; deleting the old source still produces `required current-run item or supplier is unreadable/missing`. `readLibraryItemSource` also requires exact filename/frontmatter-ID agreement.
- `tools/step5-workflow.mjs`, `gateFrontier`/`subjectScope`: original subject sets are exact strings. `validateReports` validates `now[row.id]`, all assigned reviews, source changes and deletions against those exact IDs. An old review cannot cover an ex source merely because its aliases include the old name.
- `tools/step5-guard.mjs`, centralized branch: a deleted frozen subject is expressly rejected. The original alias context protects suppliers; it does not license replacement of an original subject. It also requires original workflow-scope keys to equal the original frontier and baseline keys/hashes to match the original touchlog. Changing those seals would erase history.
- `tools/step5-judge-policy.mjs`: exact original IDs plus separately certified creations are the expected complete selection. Original Luna rows and original baseline are bound by old ID. A renamed ex is neither an unchanged original Luna subject nor an authenticated native helper.
- Native `created_items` requires new-prerequisite provenance, declared assigned consumers, a load-bearing repaired consumer, and an actual creator review. u21 created nothing; ex is the replacement answer itself, not a prerequisite of an artificially retained op. An open problem cannot consume it as a proof supplier to disguise a solution.
- Numeric metadata history explicitly preserves ID and kind and permits numeric source changes only. Quote history permits citation mirrors only. Published maintenance is for published carriers; this carrier is draft. Reporting-context recovery/withdrawal authenticates missing or withdrawn reading context, not item identity. Reader concerns and initial scope findings have distinct genuine origins; u21's real assigned fatal is neither of those. These adapters cannot be broadened by passing a creatively shaped payload.
- `freezeFrontier`/`validateFrontier` and `saveRoundState` in `step5-rounds.mjs` preserve the original ID inventory and seal. Frontier append concerns unfinished Step 1 and is not Step-5 replacement authority.

## Suggested shared projection API

Use a small new `tools/step5-original-slot-reclassification.mjs` module, not scattered alias fallbacks. Names below are proposed interfaces, not existing callable exports:

```js
previewOriginalSlotReclassification(root, run, payload) // pure read-only validation
recordOriginalSlotReclassification(root, run, payload)  // root-owned actual-hold capture
loadOriginalSlotReclassification(root, run, { current: true })
originalSlotView(root, run, { frontier, initialPack, receipt })
```

The view should return explicit immutable mappings and methods:

```js
{
  originalIds,          // exact 1472 original IDs; unchanged seal
  currentIds,           // exactly 1472 projected slots, old replaced once by ex
  originalToCurrent,   // identity except the sole authenticated old -> ex pair
  currentToOriginal,   // inverse; reject collisions, merges and chains
  currentId(original), // slot lookup only; do not use as a global alias resolver
  originalId(current), // provenance/baseline lookup only
  currentOwner(current), // original batch 21/home preserved
  transitionForOriginal(original), // exact typed record or null
  evidence             // receipt, original/current archives and native bindings
}
```

Keep source maps canonical and real: `now[ex]` is the actual ex source hash and there is no fabricated `now[old]` current carrier. A separate `historicalInitialReviewView` may reconstruct old u21 validation from archived authentic post bytes and return `historical_reviews` plus mandatory `current_review_targets: [ex]`. Its output must not be usable as current coverage. Exact old decision keys `(old, model, context_sha256)` stay untouched; the decision slot continues to have its original fatal outcome/type. Later current Sol decisions have ex IDs and real current tuples. For threshold accounting explicitly record `original_id: old` alongside current subject attribution without rewriting the original decision.

For diff/propagation introduce a typed event such as `{kind:'original-slot-reclassification', original_id:old, current_id:ex, before_guard, after_guard, before_statement_sha256, after_statement_sha256, receipt}`. This is neither `created_item` nor an excluded deletion. `licensedReplacement(old, ex, current, certificate)` must authenticate the exact receipt and actual current ex certification before the protected-deletion check can accept it. Merely matching a map or alias is insufficient. Retain fresh current review/proof-contract and Sol obligations through cached/retry paths.

Historical supporting metadata access needs a separate `supportingReclassificationHistory(history, path, expectedHash)` that returns only exact authenticated original bytes. It should compose with, rather than replace or relax, existing quote/numeric metadata/published history. The recorder must account for actual layered before/after carriers if root applies other independent metadata corrections; do not infer missing preimages from live files.

All normal callers should obtain the view from this single validator and current `frontier.json` seal. No-receipt runs receive the identity view and retain existing behavior. Historical evidence validators retain unprojected original IDs. Current work/certification/gate selectors use `currentIds`. Wherever both are required, pass both named sets; a misleading generic `frontier.ids` mutation invites historical/current confusion. Do not cache a receipt across an unvalidated state/source change.
